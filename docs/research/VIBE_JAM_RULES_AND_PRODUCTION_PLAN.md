## 1. Question

如何在 Vibe Jam #01 的实际时间、展示和投票规则下，把《残留项》做成一个可稳定演示、让其他参与者真正想玩的 AI 原生游戏，同时避免把时间浪费在活动不评分的工程完整度上？

《残留项》不是把 AI 对话框贴到普通游戏上，而是让原本被视为工具的存档系统 SAVE_03 形成记忆、偏好和有限意志。核心机制与主题直接对应，方向成立。

### 奖项与投票

奖项为“真的会玩奖”：

- 第一名：人民币 3000 元
- 第二名：人民币 2000 元
- 第三名：人民币 1000 元

投票由参赛者和嘉宾互相进行。标准不是复杂的技术评分表，而是这个机制是否让人“真的想玩”。票数一致时，现场进行二选一复投。

这意味着：

1. 玩法理解速度比后台完整度重要。
2. 可重复触发的高光比大量内容重要。
3. 五分钟内必须让观众理解“普通存档为何开始反抗玩家”。
4. 现场不能把时间浪费在解释架构、Prompt 或模型供应商。

## 3. RouterBase 与《残留项》的关系

### 适合承担

RouterBase 提供 OpenAI 兼容接口，适合通过自建后端调用聊天模型。它在本项目中只承担：

- 从 Godot 本地提供的 `allowed_decisions` 中选择一项
- 根据玩家历史调整 SAVE_03 的短句语气
- 在白名单范围内返回人格变化建议
- 在不改动主线的前提下增加不同玩家的关系差异

### 不得承担

- 不决定主线剧情
- 不创建新证据、角色或结局
- 不决定玩家是否能通关
- 不控制 99% 倒退和幽灵存档
- 不直接修改 Godot 核心状态
- Token 不得写入 Godot 客户端、仓库、日志或截图

### 推荐接入方式

```text
Godot 本地状态
→ 本地计算 allowed_decisions / targets / mutations
→ 自建 Node.js 后端
→ RouterBase /v1/chat/completions
→ Zod 校验
→ Godot 二次白名单校验
→ 合法则采用，否则进入本地 fallback
```

### 尚未确认

- 活动额度对应的具体账号和模型权限
- 目标模型是否稳定支持 `response_format` 或严格 JSON Schema
- 上海现场网络下的真实延迟
- 中文短句一致性
- 20 美元额度的有效期

因此 RouterBase 必须晚于本地垂直切片接入。

## 4. Tripo3D 与《残留项》的关系

### 适合承担

- SAVE_03 核心设备
- 老式电话
- 相框
- 物理备份芯片

### 不适合承担

- 整间办公室的全部素材
- 多套角色模型
- 运行时实时生成模型
- 用五份不同模型表达 SAVE_03 的五种状态

### 推荐生产方式

优先使用一张风格锚点图进行 Image-to-Model，而不是只靠长文本盲抽。

SAVE_03 核心建议：

- 目标格式：GLB
- 目标面数：约 3000–8000 faces
- 生成方式：低面数、PBR、固定 seed
- 状态变化：Godot 材质参数、Shader、AnimationPlayer 和裂纹遮罩
- 必要时使用 Blender 清理原点、法线、材质槽和碰撞体

Tripo 官方资料显示其低多边形生成支持固定 seed、`face_limit`、PBR 和 UV；GLB 也可以转换为 FBX、OBJ 等格式。但 `generate_parts` 与纹理、PBR、quad 存在互斥约束，不能看到“支持分件”就把所有选项同时打开。

### 尚未确认

- 活动赠送 Credits 对应 Web Studio 还是 API Platform
- 生成素材的活动展示和后续商业使用授权
- 3000 Credits 的有效期
- 实际生成风格能否与 2.5D 办公室统一

## 8. Advice

### 当前最重要的建议

不要把“高扩展、可维护、详细注释”误解成比赛当天建设企业级框架。

本项目真正需要的是：

- 状态边界清晰
- 本地规则确定
- 数据和逻辑分离
- 网络失败可降级
- 高光触发可测试
- 模块能独立替换

不是：

- 为未来十张地图预建系统
- 给每行代码写解释
- 同时维护 Windows、Web 和复杂后端
- 在核心循环未完成前生成大量 3D 素材

### 注释规范

应该详细注释：

- 为什么存在这个规则
- 状态不变量
- 非直观的边界条件
- fallback 原因
- 网络与本地状态的信任边界
- 99% 倒退等固定演出的时序要求

不应该注释：

- 变量赋值的字面意思
- 已由类型和函数名表达的内容
- 未来可能做但当前没有需求的设想

## 9. 规范文档

### 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 引擎 | Godot 4.7.1 stable，待最终确认 | 本机已安装；适合快速迭代、Control UI、动画与本地构建 |
| 脚本 | GDScript，显式类型 | 与 Godot 编辑器集成最快 |
| 渲染 | Compatibility | Windows 与 Web 兼容性优先 |
| 数据 | JSON | 行动、文本和白名单可数据驱动 |
| AI 网关 | RouterBase | 活动合作工具；OpenAI 兼容 |
| 后端 | Node.js LTS + TypeScript + Fastify + Zod | 保护 Token、双重校验和 fallback |
| 3D | Tripo3D + 可选 Blender | 快速生成少量关键资产 |
| 版本管理 | Git + Git LFS | 代码、GLB、WAV 分离管理 |

### 架构边界

```text
本地确定性核心
├── 世界状态
├── 玩家知识
├── 人格状态
├── 残留数据
├── 固定高光
└── 结局条件

可替换增强层
├── RouterBase 台词与有限选择
├── Tripo3D 生产素材
└── Demo Mode
```

### 参考同类产品时应借鉴什么

同类时间循环和叙事推理产品应重点参考：

- 信息如何跨循环形成价值
- 玩家如何快速理解失败不是白费
- 固定场景如何通过状态变化产生新鲜感
- 关键选择如何形成可复述的玩家故事
- 五分钟展示如何快速建立规则、反转和代价

不直接照搬具体剧情、角色、美术或谜题。

## 10. 电脑代开发可行性

### 可行

AI 可以完成：

- 创建和编辑项目文件
- 编写 GDScript、JSON、TypeScript 和测试
- 操作 Godot 场景树、Inspector、导入和运行
- 操作浏览器读取文档、RouterBase 和 Tripo
- 捕获截图和运行证据
- 按 Backlog 单任务循环开发

### 必须由用户处理或确认

- 登录、验证码和账号安全步骤
- API Key 创建和保管
- 注册邮箱提交
- 付费、授权与许可确认
- 最终报名、对外提交和公开发布
- 关键美术方向和最终体验判断

### 推荐制作模式

```text
用户确认单个 Task
→ AI 修改文件
→ AI 运行 Godot / 测试
→ AI 截图并记录证据
→ AI 报告风险与下一步
→ 用户确认后进入下一个 Task
```

不建议全程用鼠标在 Godot 内手写代码。代码和数据使用文件级编辑，Godot GUI 用于场景、Inspector、导入、运行和视觉验收，效率与可靠性更高。
